一、為什麼是 Markdown

一個代理系統裡流動的語言，大致分成三層：自然語言負責意義與協商，JSON 一類的結構化資料負責狀態與工具呼叫，Markdown 則是人和模型共用的工作空間，計畫、報告、記憶與技能檔都寫在這一層（Hsieh 2026，表 1）。一份 SKILL.md 剛好跨了三層：開頭是 YAML，主體是 Markdown，Markdown 裡裝的是自然語言。

層在 SKILL.md 裡擅長主要風險
結構化資料frontmatter：name、description機器可驗證格式一錯，整份技能載入失敗
半結構文本標題、清單、表格、程式碼區塊人可讀，模型可定位過時或互相衝突的指示
自然語言每一條規則的內容表達理由與例外歧義、說得不夠

有一點常被忽略：模型從來沒有「看到」排版後的 Markdown。## 和 | 對它而言只是詞元，和其他文字一起進入同一條序列。這些符號之所以有用，是因為預訓練語料裡滿是 README、技術文件與筆記，模型早已學會「## 之後是新話題」「1. 之後的東西有順序」這些文類慣例。切換下面的檢視，比較兩種讀者看到的東西。

語言學視角：標記即後設語篇

Hyland（2005）把「首先、總之、如下表所示」這類組織篇章、引導讀者的語言稱為後設語篇（metadiscourse）。Markdown 標記是後設語篇的符號化版本：## 宣告話題轉換，1. 宣告程序，表格宣告「以下各項可以逐欄比較」。對人類讀者，它們在版面上顯現；對模型，它們以詞元的身分參與預測。

二、九個符號

寫技能只需要九種標記，外加檔頭的 YAML。右欄是每一種在技能裡的典型用途；用錯地方的代價，第七節會再談。

標記寫法在技能裡用來
標題# 標題 ## 小節切出話題。一份技能只有一個 #，其下用 ##，不跳級
編號清單1. 第一步有先後順序的程序
項目清單- 一項沒有順序的並列條件、例子
粗體**重點**一段裡最不能漏看的詞，少用
行內程式碼`MRW`標籤名、檔名、必須逐字照寫的字串
程式碼區塊```markdown … ```輸出樣板。區塊裡的東西照抄，不詮釋
表格| 標籤 | 定義 |標籤集：每個標籤的名稱、定義、例子並排比較
連結[說明](references/a.md)指向參考檔；技能裡也常直接寫路徑
引用> 原文引述語料或使用者原話，與指示分開
frontmatter--- 包住的 YAML放 name 與 description，只能出現在檔案最開頭

語言學視角：工具與技能的三層

Hsieh（2026）把工具呼叫拆成三層：綱要是句法，說明是語意，何時呼叫是語用。技能沿用同一個切分。frontmatter 的格式是句法；程序與標籤定義是語意；description 與「什麼時候去讀哪個參考檔」則是語用，因為它們規定的是一段文字在什麼情境下生效。

四、三層載入

想像一面書架。找資料時你先掃書背，只抽出看起來相關的那本；翻開後讀目錄與序，需要細節時才翻到附錄。技能的載入方式相同，稱為漸進揭露（progressive disclosure）：所有技能的 name 與 description 一開始就在模型的脈絡裡，內文在觸發後才讀，參考檔則等內文指引時才讀。

五、description 是語用

description 的語力是一個條件式指令：「當情境符合 X，就讀我」。它是否生效，取決於模型能不能從使用者的話認出 X。這和 Searle 所說的預備條件同構：請求要成立，聽者得有能力、情境得合適；技能要觸發，使用者的請求得落在 description 描述的情境裡，而且模型得認得出來。

觸發失敗有兩種方向，正好對應 Grice 的量的準則。說得太少，技能在該出場時沒出場（觸發不足）；說得太多或太寬，鄰近任務也把它叫出來（誤觸發）。現行模型比較常犯前者，所以 description 寧可主動一點，寫出使用者實際會用的說法。

三句式
  1. 做什麼：一句話說清楚任務與產出。
  2. 何時用：列出使用者會怎麼說，並加上「即使對方沒有提到某某術語」。
  3. 何時不用：點名最容易混淆的鄰近任務。

八、用 Python 驗證

  
起手包附兩支程式。skill_lint.py 做的檢查和本頁相同，適合寫完後在本機跑一次；trigger_eval.py 才是真正的試金石：它把你的技能和幾個鄰居技能並列，對每一則測試請求問模型要讀哪一個，重複數次後計算觸發率。


# 1. 格式與結構
$ python tools/skill_lint.py mipvu-zh

【句法】
  ✓ frontmatter 符合規格
【語意】
  ✓ 內文結構完整：標題、程序、標籤表、輸出樣板都在
【語用】
  ✓ description 同時說明了做什麼、何時用、何時不用

# 2. 觸發測試（先用 --dry-run 檢查提示，不需金鑰）
$ python tools/trigger_eval.py tools/evals/mipvu-zh.triggers.json --runs 3

  
觸發測試的結果用精確率與召回率解讀，兩者剛好對應上一節的兩種失敗：

  

  

    
指標問的是偏低代表改寫方向

    
      
召回率該觸發的請求，有幾成真的觸發觸發不足在「何時用」補上使用者的實際說法

      
精確率觸發的請求，有幾成是該觸發的誤觸發在「何時不用」點名被誤叫出來的鄰近任務

    
  

  

  
測試集的設計比程式本身重要。最有診斷力的負例不是「今天天氣如何」，而是和你的任務共享詞彙的鄰近任務：同樣談「比喻」的文案寫作、同樣處理中文的斷詞、同樣做標註的情感分析。起手包的 mipvu-zh.triggers.json 示範了這種設計。

  

    
語言學視角：description 是一條釋義

    
寫 description 很像編詞典。釋義太窄，合法的用例被排除；太寬，不相干的用例被收進來。召回率與精確率，正是詞典學家檢驗釋義時心裡那兩把尺。差別在於，詞典的讀者是人，會用常識補足釋義的缺口；description 的讀者是模型，它補缺口的方式由訓練資料決定，所以必須實際測試，不能只靠自己讀起來覺得清楚。

  

  
程式說明見起手包的 README.md。測試結果是近似值：真實環境裡模型在更完整的脈絡下決定是否讀取技能。
